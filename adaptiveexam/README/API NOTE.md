# API NOTE

### 🚀 第一条 API：造题机器 —— 录入新题目

- **API 路径：** `POST /api/questions`
- **作用：** 这是后台管理系统的基础。管理员或老师用它把新题目存进数据库。
- **前端传给后端什么（Input）：**
  - 包含题目信息的 JSON 表单（对应 `QuestionFormDTO`）。
  - 里面有：课程ID (`moduleId`)、题干 (`questionText`)、选项数组 (`options`)、正确答案 (`correctAnswer`)。
- **后端做了什么（流程）：**
  1. **安检：** `@Valid` 拦截器先检查前端有没有漏填选项或没给正确答案。
  2. **生成 ID：** 后端自动为这道题生成一个以 `q_` 开头的唯一流水号。
  3. **格式转换：** 把前端传来的选项 List（数组）转换成 JSON 字符串，以适应 MySQL 的存储格式。
  4. **持久化：** 调用 Mapper 把这组数据（也就是 `QuestionBank` PO 对象）塞进数据库的 `question_bank` 表。
- **返回给前端什么（Output）：** 纯文本，告诉前端“添加成功”，并附带新题目的 ID。

🎤 **给组长汇报时的加分话术：**

> *“在录入题目的 API 中，我重点处理了选项数组的序列化问题。因为 MySQL 不支持直接存数组，我在 Service 层引入了 Jackson 工具包，将前端的 List 平滑转换成了 JSON 字符串再入库。”*



#### 🚀 完整数据流程：一道题目是如何存进数据库的？

当管理员在前端页面填好了一道题，点击“保存”按钮时，整个系统的齿轮是这样转动的：

#### **第 1 步：前端发车 (The Request)**

前端把表单数据打包成一个 JSON 格式的数据包，贴上快递单，目标地址写着 `POST /api/questions`，然后通过网络发送给后端。

JSON

```
{
  "moduleId": "c_001",
  "questionText": "Java是什么？",
  "options": ["语言", "动物", "食物", "汽车"], 
  "correctAnswer": "语言"
}
```

#### **第 2 步：Controller 接单 (门卫签收)**

你的 `QuestionController` 里有一个方法头上顶着 `@PostMapping`，它就是负责守卫 `POST /api/questions` 这个大门的。 当快递（JSON数据）到达时，Spring Boot 会自动把它拆包，装进你定义好的“接待员” `QuestionFormDTO` 的肚子里。并且因为你加了 `@Valid`，门卫还会检查一下里面有没有漏填的东西。

#### **第 3 步：Service 加工转换 (核心车间)**

Controller 把装满数据的 `QuestionFormDTO` 扔给了 `QuestionServiceImpl`（服务层）。这里就是工厂的流水线，核心工作是**把 DTO 转换成 PO**，因为仓库（数据库）不认识 DTO。

- **造新箱子：** `QuestionBank po = new QuestionBank();` (召唤出仓库管理员)。
- **贴条形码：** 后端用 UUID 自动生成一个 `q_xxxx` 的唯一 ID，放进 PO 里。
- **简单搬运：** 把 DTO 里的 `moduleId`、`questionText` 原封不动地复制到 PO 里。
- **🌟 核心变形（重点）：** 遇到 `options` 时卡住了！DTO 里是 `List` 数组，但 PO 需要的是 `String` 字符串。于是你请来了 `ObjectMapper`（翻译官），把数组翻译成了 `["语言","动物","食物","汽车"]` 这样一串纯文本，然后塞进 PO 的 `optionsJson` 里。

#### **第 4 步：Mapper 入库 (存入仓库)**

现在，你的 `QuestionBank` PO 已经装满了完全符合数据库要求的数据。 Service 把这个 PO 交给 `QuestionMapper`，Mapper 念了一句 SQL 咒语（`INSERT INTO ...`），这道题就稳稳地躺在你的 MySQL 数据库里了。

#### **第 5 步：返回响应 (给前端发短信)**

题目存好后，后端顺着原路返回一个 `HTTP 200 OK` 的信号，并附带一句：“题目添加成功！新 ID: q_xxxx”。前端收到信号，弹出一个绿色的成功提示框。



### 🚀 第二条 API：发卷机器 —— 获取脱敏考卷

- **API 路径：** `GET /api/questions/list?moduleId={课程ID}`
- **作用：** 这是前端学生端的核心。当学生点击“开始 Java 考试”时，前端调用此接口拉取试题。
- **前端传给后端什么（Input）：**
  - 直接在 URL 地址栏里带上想考的课程 ID，比如 `moduleId=c_001`。
- **后端做了什么（流程）：**
  1. **捞数据：** 去数据库把属于这门课的所有题目全部查出来。
  2. **反向转换：** 把数据库里的选项 JSON 字符串，重新解析成 List 数组。
  3. **⭐ 核心脱敏：** 创建一个专门用于展示的 `ExamQuestionVO` 对象，**故意过滤掉数据库里的 `correctAnswer` 字段**。
- **返回给前端什么（Output）：**
  - 一个只包含 题目ID、题干、选项数组 的 JSON 列表（`List<ExamQuestionVO>`）。

🎤 **给组长汇报时的加分话术：**

> *“为了保证考试系统的绝对安全性，发卷接口我做了严格的数据脱敏。返回给前端的 VO 模型中彻底移除了正确答案字段，从根源上杜绝了学生通过浏览器 F12 抓包作弊的可能。”*



#### 📦 场景二：发卷机器 (GET 获取脱敏考卷)

**核心任务：** 学生点击“开始考试”，后端去仓库把这门课的卷子拿出来，**擦掉正确答案**，然后发给学生。

#### **第 1 步：前端发车 (取件请求)**

学生在浏览器里点击“Java 基础测试”。前端发起一个 `GET` 请求。因为只是拿东西，所以不需要打包一个巨大的 DTO 过来，只需要在网址后面挂个牌子：`?moduleId=c_001`。

#### **第 2 步：Controller 接单 (门卫登记)**

门卫 `QuestionController` 看到是来要卷子的，并且带了 `c_001` 的牌子，立刻把这个需求报给了工厂车间（Service 层）。

#### **第 3 步：Mapper 提货 (去仓库拿原件)**

Service 车间收到需求后，立刻命令库管搬运工 `QuestionMapper` 去 MySQL 仓库里把 `c_001` 这门课的所有题目原封不动地搬出来。 **⚠️ 极度危险：** 搬运工拿出来的是 `QuestionBank` (PO) 对象，**这里面可是写着标准答案（`correctAnswer`）的！** 绝对不能直接拿给学生！

#### **第 4 步：Service 加工脱敏 (涂黑答案 & 重新包装)**

这是发卷机器最核心的一步！Service 车间拿到了带答案的 PO，开始疯狂操作：

1. **拿新盒子：** 拿出一批崭新的 **VO (`ExamQuestionVO`)** 盒子。VO 的职责就是专门包装给前端展示的数据。
2. **反向翻译：** 把 PO 里的 `optionsJson` 字符串，用 `ObjectMapper` 翻译回 `List` 数组，因为前端的按钮需要数组才能渲染。
3. **✂️ 物理剪裁（重点）：** 把题目 ID、题干、选项放进 VO 里。但是，**故意不把 PO 里的 `correctAnswer` 放进去！** 4.  这就相当于把原件上的答案用黑笔涂掉，做成了一份“安全副本”。

#### **第 5 步：返回响应 (发卷子)**

后端把装满了 VO 盒子的列表（`List<ExamQuestionVO>`）通过网络发给前端。前端拿到后，毫无顾忌地渲染在屏幕上，不管学生怎么破解，里面压根就没有答案字段！



### 🚀 第三条 API：无情判卷引擎 —— 提交试卷并出分

- **API 路径：** `POST /api/assessments/submit`
- **作用：** 整个系统的“大脑”。学生答完题点击交卷，后端负责批改、算分、给评语并存档。
- **前端传给后端什么（Input）：**
  - 一个巨大的交卷清单（对应 `SubmitExamDTO`）。
  - 里面有：考了哪门课、花了多少秒、以及**每一道题的 ID 和学生选的答案**。
- **后端做了什么（流程）：**
  1. **准备标准答案：** 根据课程 ID，从数据库查出这门课所有题目的标准答案，并放进一个 `HashMap` 内存字典里。
  2. **循环批改：** 遍历学生交上来的每一道题，去 `HashMap` 里瞬间比对答案是否正确。
  3. **存明细：** 把学生这道题选了什么、对没对，存入 `assessment_answer_detail` 细节表。
  4. **算总分：** 算出售答对比例，得出 0-100 的最终分数，并生成“Excellent”等智能评语。
  5. **存总成绩：** 把总分、耗时存入 `user_assessment_record` 主表。
- **返回给前端什么（Output）：**
  - 一张精美的成绩单（对应 `ExamReportVO`），包含最终得分、答对几道、以及智能评语。

🎤 **给组长汇报时的加分话术：**

> *“在判卷算法这里我做了两个优化。第一，我没有在 for 循环里去数据库查标准答案，而是先一次性查出来放进 HashMap 里做 O(1) 的内存比对，极大提升了判卷性能。第二，我给整个判卷方法加上了 `@Transactional` 事务注解，保证了总成绩表和答题明细表的数据强一致性，任何一步报错都会完美回滚。”*



#### 🏭 场景三：无情判卷引擎 (POST 提交试卷并出分)

**核心任务：** 学生交卷，后端快速批改、算出总分、把每一题的对错存进数据库，最后扔给学生一张华丽的成绩单。

#### **第 1 步：前端发车 (投递答题卡)**

学生做完题目，点击“交卷”。前端把答题数据打包成一个巨大的包裹——这次用的是 **`SubmitExamDTO` (接待员)**。 包裹里装着：考了哪门课、花了多少秒，以及最关键的——一个数组，里面记录了“第1题我选了A，第2题我选了C...”。

#### **第 2 步：Controller 接单 (门卫安检)**

门卫用 `@Valid` 检查包裹，确认没少漏关键字段后，把 `SubmitExamDTO` 扔进 Service 车间。

#### **第 3 步：Service 准备标答 (翻出红头文件)**

车间要判卷，得先知道正确答案是什么。于是车间让 Mapper 去仓库把这门课的 `QuestionBank` (PO) 全部拿出来。 **🌟 高级优化：** 车间没有笨拙地一道题一道题去翻找答案，而是立刻把所有答案提取出来，做成了一本字典（`HashMap` 内存缓存），题号是目录，答案是内容。

#### **第 4 步：Service 流水线批改与记录 (判卷与归档)**

车间开启流水线，拆开学生的 `SubmitExamDTO` 包裹，拿出每一道题的作答记录：

1. 瞬间去刚才的 `HashMap` 字典里查出标准答案，对比一下，得出“对”或“错”。
2. **马上建档：** 拿出一个专门记流水账的本子 **`AssessmentAnswerDetail` (PO)**，写上：张三、第1题、选了A、错了。写完立刻扔给 Mapper 存进数据库。（这就是保存答题细节）。

#### **第 5 步：Service 算分并保存总成绩**

全部判完后，算对了几道，除以总题数，得出最终得分 85 分。 拿出一个专门记大总管成绩的本子 **`UserAssessmentRecord` (PO)**，写上：张三、c_001课程、85分、用时 120 秒。扔给 Mapper 存进数据库。 （*注：第4步和第5步被 `@Transactional` 锁死了，一旦中途断电报错，前面存的细节全部作废撤回，保证不出现脏数据！*）

#### **第 6 步：返回响应 (发放成绩单 VO)**

分数算出来了，总不能把干巴巴的数据库本子 (PO) 扔给学生吧？ 于是，车间拿出了极其精美的 **成绩单包装盒 `ExamReportVO` (VO)**。 把 85分、击败了多少人、花了多少时间填进去，并且加了一句智能评语：“Excellent! Keep it up.”。 最后，把这个华丽的 VO 成绩单返回给前端！前端拿去放烟花庆祝！



### mapper,service,controller的作用

#### 🍽️ 1. Controller（控制层）：前台服务员

- **它的角色**：餐厅的迎宾兼点单服务员。它是你的后端程序与前端（用户）沟通的唯一窗口。
- **它的主要工作**：
  1. **接待客人（接请求）**：前端发来的 `GET`、`POST` 请求，全是它在门口拦下来（依靠 `@RequestMapping` 等注解）。
  2. **检查菜单（参数校验）**：看看客人点的菜对不对（比如前端有没有漏传字段，依靠 `@Valid`）。
  3. **大堂传话（调 Service）**：服务员自己不会炒菜，他只是把客人的需求整理好，往后厨大喊一声：“Service，做一份土豆牛肉！”
  4. **上菜（返回响应）**：后厨做好菜后，服务员负责端给客人（把 VO 数据转换成 JSON 发给前端）。
- **核心原则**：Controller 里**绝对不能写复杂的业务逻辑代码**，它的代码应该越薄、越干净越好，只负责“迎来送往”。

#### 👨‍🍳 2. Service（服务层）：后厨主厨

- **它的角色**：餐厅的核心主厨，掌握着所有的核心技术和秘方。
- **它的主要工作**：
  1. **核心加工（业务逻辑）**：这是整个系统最重要的地方。比如你之前写的“计算考试总分”、“把标准答案和用户答案进行比对”，这些大脑运算全在这里完成。
  2. **发号施令（调 Mapper）**：主厨做菜需要食材，但他不会自己去冰柜拿，他会喊仓库管理员（Mapper）：“给我拿两斤牛肉过来！”
  3. **保证安全（事务控制）**：炒菜不能炒一半停电了，所以主厨掌握着 `@Transactional` 绝技，保证数据要么全部保存，要么全部撤回。
- **核心原则**：所有的脏活、累活、算法计算全放在这里。

#### 🧊 3. Mapper / DAO（数据访问层）：仓库管理员

- **它的角色**：掌管地下室冰柜（MySQL 数据库）的纯粹搬运工。
- **它的主要工作**：
  1. **写 SQL 语句**：它只和数据库打交道，里面全是 `SELECT`、`INSERT`、`UPDATE` 等 SQL 语句。
  2. **搬运数据**：Service 要什么数据，它就去数据库查出来；Service 算好了什么数据，它就原封不动地塞回数据库。
- **核心原则**：它是个没有感情的搬运机器，绝对不参与任何计算（比如算分），只管读写数据库。

#### 💡 进阶拷问：为什么 Service 要分成 `Interface`（接口）和 `Impl`（实现类）？

你一定觉得很奇怪：我在 `IQuestionService`（接口）里写了一遍方法名，又要在 `QuestionServiceImpl`（实现类）里再写一遍，这不是脱裤子放屁吗？为什么不直接写一个类搞定？

在小型个人项目里，直接写一个类确实可以。但在**大厂的团队协作**中，分成接口和实现类是**绝对规范**，主要为了两大目的：

##### 📖 目的一：“菜单”与“厨师”解耦（规范先行）

- **接口（Interface）就像是餐厅的“菜单”**。它只规定了“我们餐厅能做土豆牛肉（`addQuestion`）”，但它绝对不写怎么做。
- **实现类（Impl）就是“具体的厨师”**。他负责提供具体的做菜步骤。

**好处是什么？** 假设前端开发人员和后端是同时开工的。架构师只需要把 **接口（菜单）** 写好扔给前端，前端一看：“哦，有一个叫 `addQuestion` 的方法，需要传这些参数”，前端就可以直接去写网页了。至于后端底层的厨师（Impl）怎么炒这个菜，前端根本不关心。

##### 🔄 目的二：无痛换人（多态扩展）

假设你的系统一开始只有 100 个人用，你的 `QuestionServiceImpl` 里写了一套比较基础的判卷算法。 后来系统爆火，有 10 万人同时考试，基础算法太慢了，你需要接入极其高级的 Redis 缓存判卷算法。

- **如果不分接口**：你得把原来的代码全删了重写，风险极大。
- **分了接口后**：你只需要新建一个高级厨师类 `QuestionServiceAdvancedImpl`，让他也实现那个接口（学会做同一道菜）。然后你在配置里轻轻改一行代码，把旧厨师换成新厨师。**前台服务员（Controller）一行代码都不用改**，因为对于服务员来说，他只认“菜单（接口）”，只要新厨师也会做菜单上的菜就行。



==**总结一下：** Controller 负责接客，Service 负责做菜（业务逻辑），Mapper 负责拿食材（数据库交互）。 Service 分成接口和 Impl，是为了让系统的设计图（接口）和具体施工（Impl）分离，方便团队协作和未来系统的无痛升级！==
